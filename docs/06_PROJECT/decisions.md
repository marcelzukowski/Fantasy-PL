# Architectural Decision Log

This document records the major architectural decisions of the FPL Prediction & Decision Engine.

These decisions define the intended architecture of the project.

They should not be changed implicitly during implementation.

If a future implementation or experiment suggests that a decision should change:

```text
1. document the reason,
2. provide backtesting evidence,
3. create a new decision entry,
4. explicitly supersede the old decision.
```

Codex must not silently replace these decisions with a different architecture.

---

# D001 — Do not directly predict total FPL points

## Status

```text
ACCEPTED
```

## Decision

The core predictive system will not use:

```text
features
→
total FPL points
```

as its primary modelling architecture.

Instead:

```text
football context
↓
minutes
↓
football events
↓
Monte Carlo
↓
FPL scoring
```

## Reason

FPL points are generated by multiple different football processes:

```text
minutes
goals
assists
clean sheets
saves
cards
defensive contributions
bonus
```

Direct points prediction hides these mechanisms and makes:

```text
rule changes
uncertainty
correlations
simulation
debugging
```

more difficult.

## Consequence

Models should predict football-related components first.

Direct FPL-point models may exist only as:

```text
baseline
benchmark
research comparison
```

# D006 — Optimizer, not LLM, chooses mathematical decisions

## Status

```text
ACCEPTED
```

## Decision

Transfer, squad, captaincy and chip optimization must be performed by deterministic mathematical/statistical code.

The LLM must not be responsible for selecting:

```text
optimal transfer
optimal squad
optimal captain
```

from raw candidates.

## LLM role

The LLM may:

```text
explain recommendations
summarize uncertainty
translate structured outputs into readable language
```

## Consequence

The recommendation must remain reproducible without an LLM.

# D007 — Rolling a free transfer is a first-class decision

## Status

```text
ACCEPTED
```

## Decision

The optimizer must always include:

```text
ROLL_FT
```

or equivalent no-transfer action.

## Reason

A free transfer has future flexibility value.

Using a transfer simply because one is available may be suboptimal.

## Consequence

The optimizer must compare:

```text
transfer
vs
roll
```

over a multi-GW horizon.

# D008 — Point-in-time safety is a hard requirement

## Status

```text
ACCEPTED
```

## Decision

For every historical prediction:

```text
information_known_at <= prediction_timestamp
```

must hold.

## Forbidden examples

```text
future lineup
future injury update
future player price
future manager
future transfer
future set-piece hierarchy
target-match stats
future schedule changes
```

## Consequence

Any detected leakage invalidates the affected backtest.

Predictive performance does not override this requirement.

# D009 — Historical FPL xP is excluded by default

## Status

```text

```

## Decision

Historical FPL expected-points fields must not be used as model features unless they can be proven to be:


## Consequence

Historical `xP` is classified as:
